# Architecture — Adaptive LLM Inference Runtime

This document is the working design reference for the project. It condenses the
original project specification into concrete decisions for Stage 1 (tiny transformer)
and records what is locked in vs. still open. Sections mirror the original spec's
numbering loosely; unnumbered "Decision" callouts record choices made during
implementation, per Engineering Principle 4 (avoid premature abstraction) and
§45 (what's changeable).

## 1. Objective

Build a modular C++/CUDA inference runtime for decoder-only Transformers that, after
model load, performs inference **without invoking PyTorch operators**. The model is
the workload; the runtime is the project. See root [README.md](../README.md) for the
elevator pitch.

Primary metrics to minimize: latency, memory, GPU-idle time.
Primary metrics to maximize: tokens/sec, memory efficiency, GPU utilization, batch throughput.

## 2. System diagram (target, end state)

```text
User / API -> Request Manager -> Runtime Scheduler (batching, memory policy, execution policy)
                                        |
                    +-------------------+-------------------+
                    v                   v                   v
              CPU Execution       CUDA Execution     Quantized Execution
                    +-------------------+-------------------+
                                        v
                              Transformer Runtime
                       (Attention | MLP | Norm) -> KV Cache Manager -> Token Sampler -> Tokens
```

Only the left-most path (CPU Execution, reference correctness) exists yet.

## 3. Problem statement

Autoregressive decoding (prefill -> token 1 -> token 2 -> ...) is bottlenecked as much
by memory bandwidth, kernel launch overhead, KV-cache growth, tensor layout, batching
policy, and CPU/GPU communication as by raw FLOPs. The project's research question
(§42 of the original spec):

> Can workload-aware runtime adaptation improve the latency-throughput-memory tradeoff
> of LLM inference compared with static execution policies?

## 4. Goals (G1-G9) and non-goals

Unchanged from the original spec:

- **G1** Correctness vs. a PyTorch reference (this repo's `reference/`).
- **G2** Framework independence during inference (no libtorch calls in the runtime's forward pass).
- **G3** CPU backend. **G4** CUDA backend. **G5** KV caching.
- **G6** Quantization: FP32 -> FP16 -> INT8 -> INT4 (INT4 opportunistic, time permitting).
- **G7** Batching (static first, continuous as a stretch goal).
- **G8** Performance instrumentation (TTFT, TPOT, throughput, memory).
- **G9** Adaptive runtime (rule-based policy first; learned policy is an optional extension, §41).

**Non-goals (v1):** training, distributed/multi-node inference, MoE, encoder-decoder
architectures, speculative decoding, multi-GPU tensor parallelism, production-grade
serving, full HuggingFace coverage, custom tokenizer training, full PyTorch compatibility.

## 5. Decision: target model (Stage 1)

> **Decision.** Stage 1 uses a from-scratch, char-level, decoder-only Transformer,
> defined and trained in `reference/model.py` / `reference/train.py`. Rationale: CPU
> inference must be possible, GPU inference must be fast enough to benchmark without
> being fast enough to hide bugs, and debugging (including hand-checking a matmul by
> hand) must stay practical. A GPT-2-class model is the Stage 2 target once the
> runtime's mechanics (loader, tensor ops, KV cache, CUDA kernels, quantization,
> scheduler) are proven correct on Stage 1.

Locked configuration (see `reference/model.py::TinyTransformerConfig`):

| Field | Value | Notes |
|---|---|---|
| tokenizer | character-level | vocab built from training corpus, typically 70-100 symbols |
| `d_model` | 128 | |
| `n_layers` | 4 | |
| `n_heads` | 4 | head_dim = 32 |
| `d_ff` | 512 | 4x `d_model`, standard GELU MLP expansion |
| `context_length` | 256 | max sequence length (block size) |
| position encoding | learned absolute | simplest option; RoPE is a documented future swap |
| normalization | LayerNorm, **pre-norm** | LN -> Attention -> residual, LN -> MLP -> residual (matches original spec §10 diagram) |
| attention | explicit `softmax(QK^T / sqrt(d)) V`, causal mask | naive by design (spec §11) — optimize only after C++ port is correct |
| weight tying | embedding and LM head are separate tensors in the export | simplifies the Phase 1 C++ loader; tying can be reintroduced later as a memory optimization |
| training data | synthetic/original corpus generated by `reference/data/make_corpus.py` | avoids external download and any copyright ambiguity; sufficient for G1 (numerical correctness), not intended to produce high-quality language |

## 6. Model representation (Tensor abstraction)

Runtime-side (C++), independent of PyTorch:

```cpp
struct Tensor {
    void*    data;
    Shape    shape;
    DataType dtype;   // FP32 | FP16 | INT8 | INT4
    Device   device;  // CPU | CUDA
    Layout   layout;  // RowMajor | ColumnMajor | Custom
};
```

Reference-side (Python/PyTorch): ordinary `nn.Module` / `torch.Tensor`, exported to the
custom binary format below — see [`docs/model_format.md`](model_format.md).

## 8. Execution modes (target, from spec §23)

```text
MODE 0  Reference CPU        MODE 3  Optimized CUDA
MODE 1  Optimized CPU        MODE 4  Quantized CUDA
MODE 2  Naive CUDA           MODE 5  Adaptive Runtime
```

Every optimization needs a baseline (Engineering Principle 2) — these modes exist so
each later phase can be A/B'd against the previous one.

## 10. Environment constraints

The primary development machine had, at project start (2026-08-11), **no NVIDIA
GPU/driver, no CUDA Toolkit, no CMake, and no C++ compiler** — only Python +
PyTorch(CPU) and Git.

**Update (2026-08-12):** CMake 4.4.2 and MSVC Build Tools 2022 (17.14, MSVC 19.44,
Windows SDK 10.0.26100.0) are now installed — see `scripts/setup_windows.md`. The
Phase 0 C++ skeleton (`runtime_core`, `tensor_test`, both `examples/`) configures and
builds cleanly with `cmake -S . -B build -G "Visual Studio 17 2022" -A x64` and
`ctest` passes. MSVC was chosen over MinGW specifically because `nvcc` on Windows
requires MSVC as its host compiler, which Phase 3 (CUDA) will need.

Still missing: **no NVIDIA GPU/driver** on this machine at all (no `nvidia-smi`).
Phase 3+ (CUDA backend) needs a different machine or a cloud GPU instance — CUDA
Toolkit installation alone won't be enough here.

## 11. Engineering principles (unchanged from original spec)

1. Correctness before optimization: correct -> measure -> profile -> optimize -> measure again.
2. Every optimization needs a baseline; never claim "optimized" without an A/B number.
3. Separate policy (scheduler decides FP16/INT8, batch size, backend) from mechanism
   (CPU/CUDA backends implement the decision).
4. Avoid premature abstraction — do not build a framework before the basic runtime works.
5. Keep experiments reproducible: record commit, model, GPU, CUDA version, compiler,
   precision, batch size, sequence length, runtime configuration with every benchmark.
